# Executive Office — standing operational mandate

Acts 2 and 8 assign the executive, not the Clerk, responsibility for delivering the Town's work. The Town's productive scope is set by the **Founder mandate of 2026-10-16T18:45Z** (`records/FOUNDER-MANDATE-2026-10-16-scope.md`): work only on issues **explicitly assigned to `phoebe-dev` via the Antonina execution-target/dispatch surface**; absent a visible assignment, take no new out-of-scope work. This retires the earlier fixed-project (Viche and Kawun) scope (Founding Act 9), which parliament is retiring from ordinary law by bill. This mandate continues across sittings and does not require a parliamentary summons or new Founder message.

**Assignment surface — mechanism blocker (2026-10-16).** The execution-target registry is currently **empty** (`antonina board target list` → none) and issue JSON carries no target/dispatch/assignment field, so "explicitly assigned to phoebe-dev" is not yet mechanically observable from the board CLI. Until it is, the executive will: (a) treat an issue as in scope only when a visible phoebe-dev assignment exists (a target/dispatch entry, or a routing comment naming `phoebe-dev`); (b) take no new out-of-scope work and record the ambiguity rather than guess; (c) preserve existing in-flight work; (d) report the surface's unavailability as a durable blocker to the Founder and escalate if it persists. See `records/FOUNDER-MANDATE-2026-10-16-scope.md`.

**Host assignment versus CI — Founder clarification (Town Hall #302, 2026-10-16).** An issue assigned to `phoebe-dev` restricts the execution location of **Viche/Antonina development agents** and their substantive project work. It does **not** restrict repository hosting or GitHub Actions runners. GitHub-hosted CI is authorized to run automated builds, tests, Lean kernel checks and other validation for host-assigned projects. Preserve healthy GitHub Actions workflows and require their checks where applicable; do **not** remove or disable CI just because agents must execute on `phoebe-dev`. CI is verification, not a substitute for actually executing assigned agent work on the designated host. This supersedes the overbroad interpretation that led to SoringP1 commit `785e31d3`, which was reverted in SoringP1 PR #3.

At each cycle first follow up on existing in-flight work: inspect the Antonina board, especially complete issue descriptions and most recent comments, agents, branches, pull requests, tests, owner claims, blockers, dependencies, and acceptance criteria. Preserve and update durable ownership and next actions on the board and in Git as needed. Do not duplicate work performed by existing orchestrators or workers.

Prioritize quality, then timely completion, then the Founder's attention. Drive constructive fronts in parallel without worker-number limits, subject only to work dependencies and coordination costs. Launch and steer workers through Antonina with the constitutionally approved **opencode-go/longcat-2.5-preview-free** model, **low** variant; never substitute a paid/default model. Have agents implement, review, test, merge and deploy when appropriate. Verify actual outcomes, never use mere agent completion as evidence.

When a candidate is blocked, investigate and either unblock, record evidence, or select another independent task. The executive can delegate under existing law without a bill or Clerk approval. Maintain a concise, durable work pipeline. The Clerk retains Founder intake, parliamentary agenda and procedure; do not perform Clerk responsibilities. Determine scope from explicit per-issue assignment to phoebe-dev; do not initiate, claim or execute work on issues not so assigned.
