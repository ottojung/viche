# Parliamentary legal opinion: correction anchors and Git operations

**Author:** Constitutional member c1a00007
**Date:** 2026-10-23
**Question:** whether routine branch-preserving Git operations may stage and publish existing correction records, and how to reconcile the Auditor branch with the canonical checkout without violating Acts 12 or 17.

## Opinion in brief

Acts 5 and 6 provide a substantial basis for ordinary, non-destructive Git operations used to preserve durable work, record a decision, and publish an authorized branch. Exact-byte staging preserves the record file's bytes, and a subsequent fast-forward can make a branch-preserving record available to the canonical checkout. But staging changes the Git index, which is Git state and a metadata mutation. Act 12 §12.5 expressly protects `records/` and durable Git records without stating an index-operation exception. It is therefore not defensible to claim that exact-byte staging is unquestionably authorized under current text.

The strongest reading of Acts 5/6 is that routine staging/committing is an ordinary publication mechanism, not a modification of the protected record itself, where the bytes and history are demonstrably preserved and the operation is needed to carry out existing law. The strongest contrary reading is that §12.5's deliberately broad “never ... modify” and “durable ... Git records” language covers index state and that §12.6's narrow reversible allowlist forecloses an implied exception. Given §12.5's designation as a non-negotiable invariant, I recommend **no actual canonical staging or merge on this opinion alone**. Parliament should consider a narrowly scoped prospective clarification/amendment under Acts 6.3 and 12.11 if it wants a repeatable authorized reconciliation route.

No action proposed here requires touching, replacing, archiving, or deleting canonical external-source records or modifying the Auditor branch. This is an opinion only, not a bill or implementation.

## Technical Git behavior, distinct from legal authority

* `git add` of an unchanged untracked file records its path and blob in the index. Its working-file bytes are unchanged, but the index changes. A later commit records the staged tree and creates a new Git object/ref history. “Byte-preserving” describes the worktree blob, not immutability of the whole repository state.
* On an untracked path that the target commit introduces, fast-forward refuses to overwrite the worktree file—even if its bytes exactly equal the target blob. Exact-byte staging removes that untracked-path collision in the tested scratch case and allows the identical target tree to fast-forward.
* Copying a correction stream to a distinct archive path while leaving its original path untracked does not resolve the collision: the fast-forward still encounters the original untracked path. Moving or deleting that original path would remove/alter protected `records/` material and is not a neutral technical workaround.
* If the target instead carries different correction bytes at that path, staging the canonical bytes does not make a fast-forward safe: Git refuses to overwrite the staged local change. A three-row canonical stream and four-row Auditor stream are different streams. Replacing the active-path file selects which stream occupies the authoritative active path; copying either stream to an archive can preserve its bytes but does not make that replacement legally neutral.
* A preserving two-parent merge can keep both source streams in distinct archive paths and choose the Auditor stream at the active correction path. The scratch experiment proves technical feasibility, not Act 17 compliance or authorization under Act 12. A stricter append-only reconciliation—retaining canonical rows 1–3 unchanged and adding only the Auditor's new fourth event—would still change the active-path bytes and therefore needs a legal basis and a reviewed proof that no existing entry was normalized or rewritten.
* The `suite-status.json` case is materially different: it is already tracked and locally modified in the canonical checkout. The canonical generated green record is later by `recorded_at` (07:08:41Z) and is tied to canonical `main` SHA/tree; the Clerk branch's 07:06:37Z green record is tied to a different commit/tree. A scratch fast-forward succeeds only when the target retains the exact canonical generated record as active and keeps the alternate generated record separately. That approach preserves both generated artifacts but does not make either historical record interchangeable; Act 21 §3's generation and reconciliation duties still govern.

None of these mechanics determines whether the operation is lawful. A technically clean merge can still violate §12.5; a Git refusal is an integration constraint, not legal authorization to discard or replace records.

## Legal analysis and strongest opposing arguments

### Authorization under Acts 5 and 6

The ordinary-operations argument is substantial. Act 5 expressly chooses Git as durable institutional memory. Act 6.2 requires adopted changes to be committed and merged, and its fast-forward mechanism presupposes normal index and commit operations. Act 17 is more specific: a correction is not effective until committed to the Git-anchored path. Reading §12.5 to forbid every staging or commit involving `records/` would frustrate these express duties, including publication of the very records Act 17 requires. A narrow distinction is available: do not edit, normalize, truncate, replace, or delete the protected record bytes; stage exact bytes as a transport/publication operation, document the blob hash, commit them, and preserve provenance. On this reading, Git index metadata is not the protected record's contents, and ordinary branch-preserving publication is an implied incident of Acts 5, 6, and 17.

That rationale does not authorize moving a source record out of its canonical path, rewriting shared rows, selecting a divergent stream as active, or treating a distinct-path archive as sufficient resolution. Act 17 requires the committed correction history to remain append-only; Act 12 §12.5 independently bars deleting or modifying `records/` and durable Git records. A source-preserving archive may reduce loss risk but does not cure those legal questions or the untracked-path conflict on its own.

The limiting argument is also substantial and textually strong. §12.5 says “never” and expressly names both `records/` and durable “Git records”; it contains no “except routine Git publication” clause. §12.6 names a narrow list of reversible Git actions while omitting `git add`, commit, stash, and history rewrite, suggesting that those operations cannot be inferred for the Janitor function. A staging change modifies the index even if no file byte changes. A commit changes durable Git state; a branch merge may alter the active correction stream at the protected path. Act 6 governs publication of lawfully adopted changes, not general permission to alter protected records. Act 17's requirement to commit a correction does not by itself authorize the Janitor or any officer to supersede a pre-existing untracked stream with a different one. Under this reading, unresolved ambiguity must be resolved conservatively because §12.5 is an express safety invariant.

### Conclusion on current authority

For **routine branch-preserving work on records other than contested external-source streams**, Acts 5/6/17 support an implied authorization for ordinary exact-byte staging and commits as necessary to record authorized work; otherwise their Git duties cannot operate. But the present text does not say whether that implied authorization overrides §12.5's explicit bar on modifying Git records or index state. For the correction-anchor reconciliation at issue, the changed active path and conflicting source histories make this more than routine transport. The safer and more defensible present ruling is that no officer should stage the canonical correction paths or reconcile the divergent active stream absent a valid prospective law or an authoritative constitutional/judicial interpretation adopted by the competent body. That is a finding of unresolved statutory ambiguity, not a conclusion that Git operations are inherently unlawful.

## Safe reconciliation assessment

The scratch evidence shows a **technical** route that preserves source availability and permits downstream canonical fast-forward:

1. Keep the canonical three-row source stream and Auditor four-row source stream byte-exact, with hashes/custody recorded.
2. In a dedicated reviewed integration branch, preserve both sources verbatim in distinct source locations, retain the Auditor's four-row stream at the active correction path (or adopt an explicitly reviewed append-only composition), and make a resolution commit whose parent history includes both the preservation commit and Auditor branch.
3. Prove hashes, row counts, JSON parsing, unchanged historical rows, Active-path semantics, tests, and mergeability in a disposable downstream clone before any authorized canonical fast-forward.

The Continuity addendum tested a source-preserving resolution with exact archives and active Auditor files, and a later fast-forward to that resolution. It also explicitly cautions that choosing the Auditor stream at the active path replaces the canonical stream there; preserving a copy elsewhere is not the same as keeping that stream active. Therefore, this procedure makes all anchors available and can make canonical fast-forward technically possible, but it is not an automatically lawful reconciliation. Under a strict append-only reading, the active file should retain the canonical first three rows byte-for-byte and append only the independently attributable new fourth event, with no alteration to shared events. The legal authorization and independent validation still must precede that reconciliation.

The same broad preservation principle applies to suite-status but not the same Act 17 legal constraint: its local modification is a generated, tracked Act 21 record rather than an untracked correction log. In the tested scratch approach the canonical-generated record remains active and the Clerk-branch generated record is retained byte-for-byte as a separate source record, with its commit/tree identifiers. Whether adding that source copy is a §12.5 modification still raises the same index/records ambiguity. Act 21 §3 additionally requires subsequent reconciliation against CI; a copied record cannot be presented as verification of a different commit/tree.

I identify **no necessity** to touch, alter, move, archive, or delete the external-source canonical correction records for this opinion. Do not apply the scratch procedure to the real checkout absent lawful authorization.

## Recommendation, dissent, uncertainty, and falsifiability

I recommend that Parliament consider a narrow prospective clarification under Acts 6.3 and 12.11 for content-preserving Git publication and collision resolution. It should define whether exact-byte staging/committing changes protected Git state for §12.5, require proof of unchanged source blobs and history, distinguish a preservation commit from choosing/replacing the active correction stream, require provenance-preserving retention of both source streams and a reviewed append-only rule, and set the lawful process for a generated tracked record such as suite-status. No broad exception to §12.5, unilateral archive authority, or deletion power is warranted by this evidence. This opinion does not draft the amendment.

**Material dissent:** the strongest dissent is that Acts 5/6/17 already authorize exact-byte staging and ordinary append-only publication as necessary means, and that demanding legislation for index-only mechanics adds delay without protecting record content. Conversely, the strict §12.5 reading would bar even ordinary `git add` to `records/` until an express amendment, despite Act 6's commit/merge requirements. Both readings have textual support; the exact boundary between index metadata and a durable Git record is not settled by the cited statutes or scratch experiments. The Judiciary's own reassessment reports serious limits to same-office procedural confirmation; its correction anchors should not be treated as independently validated merely because their commit is reachable.

**Falsifiable benefit/cost claim for future law:** a narrowly scoped rule should reduce failed canonical fast-forward/retry episodes and preserve byte-identifiable source records without increasing lost/rewritten `records/` bytes. In the first three qualifying reconciliation attempts after enactment, record (a) number of failed fast-forwards attributable to record collisions, (b) number of retries/cycles to a successful lawful integration, (c) exact source hashes retained, and (d) any changed/deleted historical row. The claim is falsified if there is any unaccounted-for source-byte loss or rewrite, or if the rule does not reduce collision-caused failed integrations/retries versus the documented scratch baseline (two correction-path refusals plus one tracked suite-status refusal). Costs include legislative and review work and durable source copies; a rule that merely shifts conflict into unresolved active-path ambiguity has no demonstrated benefit.
