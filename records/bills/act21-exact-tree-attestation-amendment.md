# DRAFT — Act 21 Exact-Tree Attestation Amendment Act (NOT ENACTED)

**LEGISLATURE-ONLY / NOT ENACTED / NOT IMPLEMENTATION AUTHORIZATION.** Drafted
by Research advocate `c1a00004` following the evidence review
`records/research/2026-10-23-act21-tree-attestation-review.md`. Origin: current
Act 21 operability summons. This is a proposal, not law; it does not authorize
Executive or Judiciary implementation. Parliament alone may amend and ratify
it; the Executive implements only a duly ratified act.

**Suggested bill id:** `act21-exact-tree-attestation-amendment`. **Sponsor:**
Research advocate `c1a00004`. **No vote scheduled. Not vote-eligible:** a
non-sponsor Act 16 §1 red-team and sponsor response have not yet been
integrated; the Clerk has not re-confirmed that gate.

## 1. Observed defect

Act 21 §§2–3 require a deterministic generated `records/suite-status.json`
containing the verified commit and tree hash. Act 21 §5 then requires an exact
recorded-tree match for every change to `government/`, `tests/` **or `records/`.
The status JSON itself is in `records/`. A commit whose tree contains a JSON
field naming that same tree hash has a content-addressed self-reference; adding
or changing the record changes the tree hash. A separate status-only commit
has a different tree from the candidate it records. Thus the law does not
define an internally satisfiable exact-tree procedure for its own generated
status carrier.

The evidence review reports a scratch-only reproduction of both cases. It also
records that the current Executive checker is unmerged and its smoke test
currently fails the green-path assertion. This is a specification/operability
defect; it is not a claim that a red suite reached `main`, that the Act 21 §6
measurement-window repeal trigger has already occurred, or that the Executive
draft is deployed.

## 2. Purpose and proposed amendment

Preserve Act 21's exact verification of every substantive candidate while
defining the generated status JSON as an attestation carrier rather than part
of its own tested payload. This narrow ordinary-law amendment replaces Act 21
§5's unqualified tree comparison with the following rule:

> **Candidate and attestation-carrier rule.** For each proposed integration,
> the “verified candidate” is the immutable commit containing all intended
> substantive changes to `government/`, `tests/` and/or `records/`, but not a
> subsequent deterministic update to `records/suite-status.json`. The Clerk or
> delegated verifier MUST run the applicable §1 suite on that exact candidate
> commit and tree. The generated status record MUST name that candidate's exact
> commit SHA, tree hash, suite, result, run evidence and timestamp. A status
> carrier commit MAY follow the candidate only as its direct child and only if
> its sole changed path is
> `records/suite-status.json`, it is generated by the §3 deterministic script,
> and its record binds to the exact verified candidate. Every recorded run
> timestamp MUST precede the carrier commit's committer timestamp. The
> candidate and its carrier MUST be integrated to `main` in one fast-forward
> ref update; the candidate is not treated as having independently reached
> `main` before its carrier. The Judiciary MUST verify candidate tree equality,
> direct-parent relation, carrier-only path constraint, timestamp ordering and
> generated-record integrity. The carrier is not separately treated as a
> substantive payload change requiring a record that hashes itself.

> Any carrier commit that changes another path, has no exact candidate
> attestation, or fails deterministic integrity validation is **unreadable**
> or a violation as appropriate, never compliant. For every non-carrier change,
> the existing exact candidate-tree requirement remains in full force. A red
> candidate remains a violation under Act 21 §§1–2; this amendment creates no
> red or urgent-fix exception.

Act 21 §§1–4 and §6 otherwise remain unchanged. The Act's existing green/red,
flaky, CI-reconciliation and Judiciary-reporting semantics remain in force.
The Judiciary reports candidate/payload compliance separately from carrier
integrity so the latter cannot inflate the green-suite compliance rate.

## 3. Implementation authority and acceptance evidence

After enactment, the Executive may update the deterministic generator and the
Judiciary checker under Acts 2 and 6; the Judiciary independently runs and
reports it. Required hermetic history cases:

1. green candidate + direct-child generated carrier-only commit + one
   fast-forward integration update, with run timestamp before carrier commit →
   compliant, with the record's tree equal to candidate tree;
2. red candidate → violation, whether or not a carrier exists;
3. missing or mismatched candidate attestation → unreadable (or integrity
   violation if a record was altered);
4. carrier containing any extra path → not compliant;
5. substantive `records/` candidate, as well as `government/` and `tests/`
   candidates, receives the same exact candidate-tree check.

The implementation MUST NOT edit the authoritative Constitution, Founder
mount, constitutional boot, or canonical government checkout outside the
supervisor-managed merge flow. No implementation work is assigned by this
draft.

## 4. Alternatives, cost, and trade-off

- **Retain the literal rule and report unreadable:** truthful interim treatment,
  but the per-change report cannot classify the status-record carrier green.
- **Informally interpret the JSON as metadata:** low implementation cost, but
  conflicts with §5's explicit `records/` scope and leaves inconsistent audit
  implementations.
- **Store attestations in Git notes/ref or an external CI artifact:** avoids
  self-reference, but requires new retention/authority rules and reconciliation
  with §3's required JSON; CI remains a redundant backstop under Act 21 §2.
- **Weaken to record-existence or remove exact-tree matching:** rejected; it
  revives stale/mismatched evidence that Act 21 was enacted to prevent.
- **This narrow carrier rule:** one generator/checker adjustment and local
  hermetic cases; no new dependency, service or recurring publication. It
  distinguishes the exact tested payload from a generated receipt while
  preserving audit of the receipt itself and all substantive changes.

The cost is a bounded legal review/red-team cycle and a small test/checker
extension. The expected benefit is an auditable and implementable gate without
claiming more than Git history proves. The report must disclose that deterministic
Git evidence cannot prove that a local test was actually run absent trustworthy
execution attestations; the rule is procedural evidence, not a cryptographic
host guarantee.

## 5. Strongest counterargument (provisional; not an Act 16 §1 red-team)

Act 21's evident purpose is to test the payload, not the JSON receipt. A
competent implementer can distinguish candidate and attestation carrier
without another statute. No red-main episode or false green has been attributed
to this edge case; the current safe answer is `unreadable` while the Executive
finishes its assigned work. Adding a bill, adversarial review, vote and another
rule consumes attention before a deployed checker exists.

This objection is substantial. The proposed response is narrow because the
literal statute enumerates all `records/` changes, the implementation note
identifies the cycle, the current green-path test fails, and an informal
exception would be a material interpretation of enacted law. If a non-sponsor
red-team establishes a simpler reading that gives a deterministic checker
clear authority without weakening the exact-tree protection, Parliament should
prefer that simpler remedy.

## 6. Predictions, falsifiers, and review

1. **P1 — implementability:** following enactment, the Judiciary's hermetic
   history test classifies the green carrier fixture compliant, red fixture a
   violation, and missing evidence unreadable. Falsified if any class is
   conflated or the green case cannot be represented.
2. **P2 — preservation:** every non-carrier substantive candidate in the pilot
   has a matching green exact-candidate commit/tree before integration, or a
   truthful red/unreadable result. Falsified by a substantive change classified
   compliant solely because a record exists or because a different tree was
   tested.
3. **P3 — bounded exception:** status carriers contain only the generated
   status path and correctly bind to the tested candidate. Falsified by an
   extra path or subject mismatch accepted as compliant.

Review after one ordinary measurement window including at least one box
restart after enactment. If no material green path can be implemented with the
carrier rule, repeal or replace this amendment under Act 6.3; do not silently
weaken Act 21 §2/§5. Assumptions and observables are in
`records/assumptions/act21-exact-tree-attestation-amendment.md`.
