## Strongest case against the draft as written

The technical premise is credible: a status JSON cannot include its own final
containing tree hash, and a subsequent status-only commit has a different
tree. The proposed payload/carrier model is promising. The present operative
text nevertheless cannot yet support a determinate compliant result: it
replaces §5 while asserting §§1–4 remain unchanged, and leaves key Git
history and evidence predicates unspecified. The truthful interim remains
`unreadable`; there is no demonstrated red-main incident or §6 repeal trigger
that requires relaxing that safe posture now.

### O1 — The carrier exception conflicts with unchanged §§1–4 (blocker)

The proposed verifier tests the candidate parent, while the final carrier is
the tip integrated to `main`. Act 21 §2, as quoted and analyzed in the pinned
review, requires verification of the exact commit being merged; §1 scopes
`records/` changes; and §3 generates status from that verification. Section 5
replacement plus the phrase “carrier is not separately treated as a
substantive payload change” does not expressly amend those other duties. If
they remain controlling, the carrier itself is within scope; if the candidate
stands in for the carrier, §2 has been redefined. A checker cannot know which
reading is law.

**Required repair:** explicitly amend or qualify the operative clauses that
define which object §1 tests, what §2's “exact commit being merged” means for
the two-commit integration, and what §3 may record. The act must state whether
the carrier is exempt from payload-suite execution and why; avoid saying
“§§1–4 remain unchanged” where the new rule necessarily changes their
application. A hermetic green case should demonstrate the enacted reading,
not merely the desired output.

### O2 — Candidate/base and intervening history are not mechanically bounded (major)

“All intended substantive changes” is intent, not a checkable predicate. A
branch can contain several commits since `main`; testing only the selected
candidate's final tree may leave newly reachable intermediate substantive
commits untested, depending on whether Act 21 audits commits or published
payload. The draft does not name the integration base, require a direct-child
candidate, or otherwise enumerate which commit range is covered. A direct
candidate→carrier parent link does not settle that range.

**Required repair:** name the pre-integration `main` base and objectively
constrain the candidate relation to it, or require verification of every
intervening commit under a clear rule. Define supported cases for rebases,
deletions/renames and merges; reject unsupported shapes as unreadable. Add
fixtures with an extra substantive intermediate commit and a rebased or
non-linear range.

### O3 — Carrier path and topology need pinned Git semantics (blocker for merge carriers)

“Sole changed path” is not a deterministic predicate on a merge commit until
the diff comparison and topology are specified. Prior c1a0000b scratch review
reports that plausible Git diff commands on one merge carrier yielded
different changed-path sets, and some yielded an empty set. The draft's
“direct child” phrase does not explicitly prohibit a two-parent merge, or
identify which parent governs directness. Thus extra substantive paths can be
missed by an otherwise plausible checker.

**Required repair:** prohibit merge carriers or define a single-parent carrier
and pin the exact parent/base comparison, path/mode/rename treatment, and
allowed ref transition. Include an adversarial merge-carrier fixture with an
extra path and require it to fail closed. Check generated-file integrity as
well as path identity.

### O4 — One fast-forward update is not an auditable integration predicate (major)

The draft says candidate and carrier reach `main` in one fast-forward ref
update, but does not say which ref's before/after values the Judiciary must
verify, or how those values prove that no extra commit rode in the update.
Nor does it define whether “one update” refers to a local command, observed
remote ref transition, or a report. The candidate→carrier relation alone
cannot prove integration started from the named current `main` base.

**Required repair:** specify the exact ref and required old/new object IDs,
which must bind to the named base and carrier; require one linear transition
from base through the complete candidate to the sole carrier; classify
non-fast-forward, unexpected ref values, and extra commits as unreadable or
violation. Add before/after ref and extra-commit fixtures.

### O5 — Timestamps and self-reported records are consistency evidence only (major)

The proposed rule makes run timestamp < carrier committer timestamp a MUST.
Git committer timestamps and JSON run times are caller-controlled; their
ordering cannot prove the suite ran, nor establish trustworthy chronology.
The draft does disclose in §4 that Git evidence is not a host guarantee, but
the operative MUST risks letting the compliance label imply stronger evidence
than it contains. Prior c1a0000b review reports a scratch fixture in which a
future-dated carrier satisfies the ordering without a suite execution.

**Required repair:** state in the operative rule that timestamps establish
record consistency only and are forgeable, not execution authenticity. Specify
the record fields the checker validates (suite, candidate commit/tree, each
required run/result, evidence digest, verifier identity, carrier parent/path)
and fail closed on absence or mismatch. If the law intends execution
authenticity, name a trusted source and its authority/retention rules; otherwise
expressly limit the claim to procedural Git evidence.

### O6 — Legislation now versus truthful unreadable is a live counterargument (major)

The issue establishes no red suite reaching `main`, no false green, and no
§6 repeal trigger. The current checker is not merged and its smoke test
classifies green as unreadable. Continuing to report unreadable is the
lowest-cost faithful interim; it earns no compliance credit and can impose
real integration delay, but that delay is not quantified in the pinned
artifacts. An informal metadata interpretation is attractive but conflicts
with §5's express `records/` coverage. External notes/CI avoid recursion but
need authority, retention, availability and reconciliation with §3's JSON.
Weakening exact-tree matching or accepting record presence is unacceptable.

**Recommendation:** retain unreadable until either (a) the sponsor repairs the
operative clauses and the hermetic suite proves green candidate/carrier,
red, missing/mismatched evidence, extra-path, intervening-commit, merge and
timestamp cases; or (b) the Clerk records a clear interpretation grounded in
existing text without silently discarding §5 scope. The need for clarification
is well supported; the current §5-only remedy is not yet operable enough to
advance.

## Strongest argument in favor

The enacted Act's evident purpose is to test the substantive candidate, not a
receipt describing that test. The explicit §5 `records/` scope makes leaving
that distinction to informal convention unstable across implementers. A
metadata-only child carrier bound to an exact candidate can preserve exact
verification of all substantive changes without a new service, while
unreadable forever is costly and earns no green compliance. A narrow statutory
definition may therefore be the durable remedy. This argument supports
revising the bill, not treating its current unresolved clauses as sufficient.
