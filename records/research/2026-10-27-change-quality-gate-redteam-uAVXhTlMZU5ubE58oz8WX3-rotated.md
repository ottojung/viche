## Stance

**Oppose v3 as drafted pending material narrowing/clarification and explicit
operational proofs.** The objective—avoid red governance code on `main`—is
sound, and R1 is a concrete failure. The statute now includes several useful
controls, but its *operative enforcement path* does not actually guarantee a
pre-push refusal, while local mandatory gates impose substantial serial cost
and rely on soft, mutable host records. In this repo the gap is not hypothetical:
`.github/workflows/bootstrap.yml` still runs on `push` and `pull_request`, not
as a required check, and the statute expressly declines to rely on CI as the
gate. A green full suite is valuable evidence; neither a passed suite nor a
local script invoked by an office is an access-control boundary against a
direct push.

## Strongest case against

### 1. The declared gate is still a process promise, not a block

Act 21 requires an authoring office to run before push/merge and the Clerk to
verify the exact commit, but its enactment does not change repository settings.
The current workflow listens to both push and PR events and only runs
`sh tests/run-all.sh`; a failing run reports after a direct push has already
updated `main`. The law itself says post-merge CI is only a backstop and the
required-check setting is Founder-controlled. `government/reviewed-merge.sh`
does perform a suite run on its constructed candidate, but it is a convenience
path and not the only route that can update `main`; ordinary Git push remains
available. A planted test only demonstrates refusal if the attempted
publication path is itself mandatory and all alternative pushes are actually
prevented or detected as violations. A cooperative office that chooses not to
push a red candidate is not proof of enforcement. P1a's prescribed refusal
through local verification can prove that script refuses, not that every path
to `main` is gated.

**Falsifier:** demonstrate a direct push of a red suite candidate can reach
`main` without a required check or other effective publication control. The
draft predicts this only if the office disobeys; it does not supply a technical
mechanism preventing it.

### 2. Exact tree binding does not establish the test ran on that tree

The current tree-hash requirement materially improves auditability, and the
installed `suite-status.sh` checks out the selected commit in a detached
worktree before running. But the historical compliance checker must trust the
status JSON and, for prospective pre-push receipts, external state under
`VICHE_STATE_ROOT` plus a publication event emitted by `reviewed-merge.sh`.
The checker explicitly notes that this chronology depends on the delivery host,
filesystem and writer. The receipt is copied from the generated record and
publication event is generated by the same host-side path; this binds artifacts
to each other but is not an independent signature or immutable CI attestation.
An office able to write both can fabricate consistent output hashes, timestamps
and events. Tree equality proves identity of source, not test execution or
truthfulness of the result. That limitation is material when the Act calls the
result durable/auditable and predicates compliance on positive evidence.

**Falsifier:** show a record/event pair accepted by the checker after no test
execution occurred, or demonstrate the audit cannot distinguish it from a real
run. Require the bill to name this as an explicit trust assumption and avoid
describing such records as proof.

### 3. The universal full-suite mandate is expensive and currently flaky

The v3 bill itself reports a full suite run over 120 seconds; its pre-enactment
seat red-team measured `tests/janitor-smoke.sh` failing 2/3 runs. v3 responds
with two consecutive red runs to classify a block. This reduces a one-off
false block but doubles work on any first red and does not address a false green
or correlated nondeterminism. The actual suite includes `tests/boot-smoke.sh`,
which performs repeated complete bootstrap/worktree setup; `run-all.sh` also
repeats some integration coverage. Running it locally for authoring and again
for Clerk verification serializes offices and duplicates effort; CI then runs
again after push. Under load or a flaky test this can delay changes or encourage
informal bypasses. The bill lacks a hard total latency/availability ceiling,
escalation SLA for an unavailable verifier, or a safe mechanism to distinguish
environmental failure from product regression. “Two reds” is not a liveness
guarantee: if each run has intermittent failure, legitimate changes can remain
blocked indefinitely.

**Falsifier:** measure the observed time from candidate readiness to merge over
windows, including retries and Clerk/delegate queueing; compare to baseline and
show repeated red-green patterns do not cause unreasonable delay. Current text
has no threshold at which the burden triggers review.

### 4. Records-only scope can permit relevant governance regressions

The law scopes a change consisting only of `records/` paths to
`tests/records-smoke.sh`, whose implementation only searches tracked-area file
types for merge-conflict markers. It does not evaluate bill digests, tally
consistency, JSON/schema validity, suite-status chronology, or the effect of
records consumed by runtime tools. A records change can therefore break an
operative input while passing the scoped smoke check. Conversely, `run-all.sh`
does not establish that every historical record is valid; it has focused smoke
tests but not a general semantic validator. The Clerk second-office exception
only reproduces the same limited check and cannot make it more comprehensive.

**Falsifier:** plant a malformed or inconsistent record that is consumed by a
governance workflow, show `records-smoke.sh` green, and observe the break after
merge. The legislative record is itself part of the governed system, not merely
text exempt from functional quality checking.

### 5. Change classification and merge-candidate identity are underspecified

The law distinguishes “records-only” from any other qualifying path, but the
auditor classifies changes by first-parent path sets. Mixed changes are required
to use the full suite, but the statute and routine workflow do not explain how
to handle merge commits, rebases, multiple commits in a delivery branch, or a
commit whose parent changes after a local verification. `reviewed-merge.sh`
does create and verify an exact synthetic merge candidate, which is a strong
implementation improvement; however the governing text calls for a Clerk run
on the exact commit “being merged,” and the CI event does not protect a later
direct push or rebase. A status entry included in the same commit cannot be
pre-commit chronology evidence; prospective external receipt logic handles
that only for its particular delivery path. The legal obligation should specify
candidate tree identity and require re-verification after every rebase or merge
resolution, regardless of authoring route.

**Falsifier:** submit a branch that is verified, then alter its merge base or
resolve a conflict to a different tree; if the new result can publish using the
old receipt, the exact-candidate promise has failed.

### 6. Urgency and Clerk unavailability still create a discretion bottleneck

V3 usefully defines an urgent fix as repairing a recorded red-main incident and
requires a declaration with incident reference. But the declaring office
creates the record and invokes the exception; no independent pre-publication
determination is required. If the Clerk is unavailable, Act 6.2 substitution is
permitted, yet the operative text does not identify a concrete substitute
selection/rotation or a maximum delay. Thus a high-pressure repair can wait for
an office or use a self-declared route that the same actor later audits. The
one-cycle (restart-to-restart) deadline permits a red main to persist for up to
a restart interval, and escalation to the Clerk and Resource steward still
depends on institutional availability. These are discretion and liveness
risks, not solved merely by making the condition observable.

**Falsifier:** a recorded red persists because the Clerk or delegate is
unavailable, or a routine change is recorded as urgent and not independently
challenged. Specify an automatic fallback verifier and a shorter measurable
response target for red main.

### 7. The outcome metric can reward documentation rather than quality

The installed checker classifies absent evidence as `unreadable`, not red. This
is epistemically correct, but it creates a large distinction between “zero
changes reached main red” and “zero changes had provable pre-push green.” P1
counts only a red result surviving the rerun policy, while missing/inconsistent
receipts can remain unreadable. P3 checks status record and CI reconciliation;
P4 checks a Judiciary report. All can pass while exact run authenticity remains
unverifiable, or while a quiet window has very few qualifying changes. P1a is
therefore necessary but too narrow if it tests only the verifier script, and
the review window needs a minimum number/type of exercised changes or explicit
“not exercised” outcome. The newer checker’s unreadable category is an
important protection against false claims, but it should count as a coverage
failure for any claim of demonstrated gate effectiveness, not as neutral
success.

**Falsifier:** an evaluation reports the Act effective with no actual controlled
red submission, or reports high compliance while a material fraction of changes
are unreadable. Publish both the raw counts and a coverage threshold.

### 8. CI is being used as evidence but denied authority without closing the gap

`.github/workflows/bootstrap.yml` runs the full test suite on every push and
pull request with `fetch-depth: 0`, providing historical Git context, but it
does not specify a concurrency/cancellation policy, required status check, or
pre-merge-only gate. The proposal rejects CI as sole verifier because branch
protection is not controlled by Parliament, yet Act 21 §3.3 requires periodic
reconciliation against CI and the operational implementation uses CI result as
an audit comparison. This is a reasonable division only if the statute openly
states that technical prevention is unavailable and frames itself as a
procedural duty with a measured violation detector. It currently opens with
“a change reaches main only if” the suite is green and claims broken code
The report should require CI to be green on every PR, state direct-push residual
risk, and reserve any no-red guarantee for a future Founder-authorized
required-check configuration.

## Constructive alternatives

1. Keep the exact-candidate verifier and audit script, but describe them as a
   **procedural pre-publication requirement**, not a technically enforced gate,
   unless all main-update routes are protected by a required check or equivalent
   access control. Preserve Founder authority over repository settings.
2. Use the PR workflow as the standardized independent run and publish its
   commit/tree-bound result; require Clerk review on the exact merge candidate.
   If a required-check setting cannot be enabled, explicitly record residual
   direct-push risk and make any bypass detectable as a violation.
3. Add a status schema and checker test for fake receipts/events, malformed
   records, rebases, merge commits, and mixed records/code changes. Separate
   artifact identity from execution authenticity in the report.
4. Report a per-window table with qualifying changes, compliant, red,
   unreadable, rerun count, runtime and not-exercised status. Set a minimum
   coverage threshold before claiming efficacy; do not count unreadable evidence
   as green.
5. Keep the urgent-red repair path, but require the declaration to name an
   existing incident, automatically notify the independent checker, and use a
   documented alternate verifier when the Clerk is unavailable.
